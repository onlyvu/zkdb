# zkDB: circuits, VM and toolchain

This file is the reference for the parts under the dashboard: the two Noir circuits, the op format and the toolchain. The system view, diagrams and threat model are in [ARCHITECTURE.md](ARCHITECTURE.md). Everything described here is in the code and deployed on Avalanche Fuji; the list of things not built is at the end.

## Components

| Path | Role |
|---|---|
| `circuits/zkdb` | Noir library: Poseidon2, Merkle path, op semantics |
| `circuits/batch` | Batch circuit: applies exactly `K = 16` ops to a root |
| `circuits/claim` | Claim circuit: "a card in this root has at least N points" without naming the card |
| `contracts/src/ZkDB.sol` | Op queue, roles, co-signed corrections, batch verification, root |
| `contracts/src/PointsGate.sol` | Perks unlocked by a claim proof against the root |
| `contracts/src/icm/` | `RootRelay` (sends the root over ICM), `RootMirror` (holds it on the other L1) |
| `contracts/src/verifiers/` | `BatchVerifier.sol`, `ClaimVerifier.sol`: UltraHonk verifiers generated by `bb`, never edited by hand |
| `packages/zkdb` (`@zkdb/core`) | TypeScript mirror of the tree and VM, batch builder, claim witness builder, provers (noir_js + bb.js) |
| `packages/dashboard` | React dashboard, API server (sign-in, batch prover, claim relayer), deploy and demo scripts |
| `scripts/` | Pinned tool versions, tool check, circuit and verifier build |

## Data model

- Tree: binary Merkle tree of depth 20 (about one million rows), hashed with Poseidon2 over BN254. A node is `H(left, right)`. An empty leaf is `0`.
- Row: a table id and six fields. `leaf = Poseidon2(table_id, f0..f5)`. Every value is a BN254 field element.
- Row ids are handed out by `ZkDB.sol` in order when a row is inserted, up to `2^20`.
- Data availability: every op is emitted in `OpQueued` and is a public input of the batch proof, so anyone can rebuild the tree from chain data.
- Member row of the points table: `[card number, balance, card key, 0, 0, 0]`, where `card key = Poseidon2(card secret)`.

## The op format and the batch circuit

An op is nine field elements: `[opcode, rowId, a, v0..v5]`.

| Opcode | Meaning | Fails (ok = false) when |
|---|---|---|
| 0 NOOP | nothing; pads a batch to 16 | never |
| 1 INSERT | `a` = table id, `v0..v5` = the fields | the leaf is not empty |
| 2 SET | `f[a] = v0` | the leaf is empty, or `a > 5` |
| 3 ADD | `f[a] += v0` (u64) | the leaf is empty, `a > 5`, `f[a]` or `v0` is not a u64, or the sum overflows |
| 4 SUB | `f[a] -= v0` (u64) | the leaf is empty, `a > 5`, `f[a]` or `v0` is not a u64, or the result is negative |
| 5 DELETE | the leaf becomes `0` | the leaf is empty |

The points ledger uses ADD for an award, SUB for a redemption and SET for a correction, all on field 1 (the balance). `v1` carries a reason code. The circuit does not read `v1` for these opcodes, but it is part of the op, so it is hashed on-chain and bound by the proof like the rest.

`circuits/batch/src/main.nr` has these inputs:

| Input | Public | What |
|---|---|---|
| `old_root`, `new_root` | yes | the root before and after the batch |
| `ok[16]` | yes | whether each op applied |
| `ops[16][9]` | yes | the ops, padded with NOOP |
| `witnesses[16]` | no | for each op: the row it touches (or "empty") and its 20 Merkle siblings |

For each op the circuit checks that the witness row hashes into the running root, applies the op, and computes the next root. A failed op leaves the root unchanged and sets `ok[i] = false`; the batch stays valid. The prover cannot fake a failure or a success, because the witness is tied to the running root and `ok[i]` follows from it.

Size: 110,200 gates, 162 public inputs. Proving takes about 1 s with bb.js on an M2 Max (see [benchmarks.md](benchmarks.md)).

## The claim circuit

`circuits/claim/src/main.nr`:

| Input | Public | What |
|---|---|---|
| `root` | yes | the root the claim is made against |
| `table_id` | yes | the points table |
| `min_points` | yes | the perk's threshold |
| `perk_id` | yes | which perk |
| `nullifier` | yes | `Poseidon2(secret, perk_id)`: one per card and perk |
| `pickup` | yes | hash of a one-time pickup code the member's device makes; the claim is recorded under it and `collect(code)` hands the perk out once |
| `row_id`, `row[6]`, `siblings[20]`, `secret` | no | the member's row, where it sits, and the card secret |

It asserts four things: the row is in the root; `row[2] = Poseidon2(secret)`; `row[1] >= min_points` as u64 values; the nullifier is right. Proofs use the zero-knowledge flavour of UltraHonk (`verifierTarget: 'evm'` in bb.js), so the proof reveals nothing about the private inputs. The circuit has 6 public inputs. It proves in about 0.2 s in Node and 1 to 4 s in a browser.

What the claim hides and what it does not: balances are public, so an observer knows which cards could have claimed (the dashboard shows "Cards that qualify"). The claim hides which of them did. A perk two cards qualify for hides little.

## ZkDB.sol

- Roles: `owner` adds writers (`setWriter`), gives each table to one writer (`setTableOwner`) and can give a table an auditor (`setTableAuditor`). Ownership moves in two steps (`transferOwnership`, `acceptOwnership`).
- `insert`: only the table's writer. `enqueue` (SET, ADD, SUB, DELETE): only the writer who owns the row's table today, so a new treasurer inherits every row.
- Redemptions and corrections: on a table with an auditor, `enqueue` refuses SUB, SET and DELETE. The writer calls `proposeChange`; the op enters the queue only when the auditor calls `approveChange` with the same op. `declineChange` closes a proposal for good. One signer can still insert a member and ADD points.
- Queue: each op is stored as `keccak256(abi.encode(op))`; the full op and the account that asked for it are in the `OpQueued` event. An op with a value `>= P` is refused at the door, so no queued op can make the circuit unsatisfiable.
- `submitBatch(proof, newRoot, ok, ops)`: anyone can call it with the next 1 to 16 queued ops. The contract checks each op against the stored hash, builds the public inputs with its own `root` as `old_root`, and calls the verifier.
- Root history: `rootSeen[root]`, and `batchHead(root)` returns how many ops had been consumed when that root was set.
- `ok[]` is only in the `BatchSubmitted` event. The contract does not call writers back.

## Toolchain

Pinned in `scripts/versions.env` and `packages/zkdb/package.json`: nargo `1.0.0-rc.5`, bb and `@aztec/bb.js` `5.0.0`, `@noir-lang/noir_js` `1.0.0-rc.5`, Node 20 or later, Foundry.

`contracts/foundry.toml` uses `via_ir = false`: solc 0.8.30 cannot compile the optimized verifier with `via_ir` on (see [benchmarks.md](benchmarks.md)).

The compiled circuits (`circuits/target/batch.json`, `claim.json`) and both verifiers are committed, so running the project needs no Noir toolchain. `./scripts/build-circuits.sh` rebuilds them and produces the same circuit bytecode and the same verifier source (checked on 18 Nov 2026). It uses `bb` from `~/.bb` if installed, otherwise the same 5.0.0 binary that ships inside `@aztec/bb.js`.

A circuit, its verifier and its proofs go together. After changing circuit logic, run `./scripts/build-circuits.sh` and `npm run gen:fixture -w @zkdb/core`, or proofs will not verify on-chain.

## Build and test

```sh
git submodule update --init --recursive
npm ci
(cd contracts && forge test)             # 42 tests, real proof fixtures
npm test -w @zkdb/core                   # 30 tests, proves a batch and a claim
npm test -w @zkdb/dashboard              # 73 tests, starts anvil
npm run typecheck -w @zkdb/core && npm run typecheck -w @zkdb/dashboard

./scripts/install-tools.sh               # only to rebuild circuits: nargo
./scripts/build-circuits.sh
(cd circuits && nargo test --workspace)  # 28 tests
```

## Not built

- Private balances. Ops are public; only the claim hides something (which card claimed).
- Member-signed redemptions. A treasurer can still record a redemption the member did not make. It is public and names the treasurer, but nothing stops it.
- A sequencer that proves the queue on its own. Someone with a role presses *Prove*, or uses the TypeScript library.
- The receiving side of the root relay on Dispatch (`RootMirror` and a second `PointsGate`). The contracts are written and tested with a mock messenger, and `npm run deploy:mirror -w @zkdb/dashboard` deploys them; we had no gas on Dispatch.
- A batch larger than 16, and a design that posts ops only inside `submitBatch` (see [gas-comparison.md](gas-comparison.md)).
